# Wykrywanie niezgłoszonych wpłat — PL-07 / MM-24a

Implementacja lokalna: właściciel otwiera „Show wallet deposit monitoring” w centrum wyjątków, wybiera NIM/USDT i uruchamia monitoring z powodem. NIM importuje historię dostępną w skonfigurowanym węźle od najnowszych transakcji wstecz; USDT wymaga jawnego pierwszego bloku. 0 oznacza import od początku dostępnej historii i może wymagać wielu stron. UI pokazuje postęp i błędy. Wstrzymanie/wznowienie zachowuje checkpoint. API restart=true pozwala świadomie rozpocząć ponowny odczyt, nie usuwa istniejących obserwacji.

Jedna obserwacja ma aktywo, sieć, odbiorcę, hash, indeks zdarzenia, nadawcę, kwotę atomową, blok i stan potwierdzenia. Dwie takie same kwoty nie są scalane. Powtarzane strony nie tworzą duplikatów. Lista pokazuje ewentualne zgłoszenia tego samego hasha jako diagnostykę, bez automatycznego przypisania do zamówienia. OBSERVED nie oznacza otrzymanej płatności; FINALIZED wynika z kontroli kanonicznego bloku i finalności w adapterze. Brak receipt nie jest definitywnym dowodem błędnej transakcji. Skaner nie zapisuje sprzedaży, nie odbiera magazynu, nie realizuje zamówienia i nie zleca zwrotu.

Postęp odczytu i cała strona zapisują się w jednej transakcji. RPC działa poza transakcją bazy. Dzierżawa chroni przed dwoma skanami, a zmiana konfiguracji blokuje spóźniony zapis. NIM odczytuje po20 transakcji; Polygon adaptacyjnie zmniejsza zakres i stronicuje także wiele zdarzeń z jednego bloku. Niepotwierdzone obserwacje ponownie sprawdzane po10 na przebieg. Worker co60s obsługuje najstarsze konfiguracje (do20 na przebieg). WALLET_DISCOVERY_ENABLED=1 włącza worker; ręczny skan działa także bez niego.

Migracja 0035_wallet_discovery.sql. RPC: istniejące NIMIQ_RPC_URL/NIMIQ_NETWORK oraz POLYGON_RPC_URL. Wymagany węzeł Nimiq obsługujący getTransactionsByAddress i historyczne bloki oraz Polygon z eth_getLogs/receipt/finalized. Nie wykonano realnego odczytu tych hostów w tej implementacji. Nie wykonano rzeczywistych przelewów. Pokrycie historii zależy od źródła i ustawionego początku, jest pokazywane w UI; nie ogłaszamy zaimportowania całego portfela przed zakończeniem odczytu.

Weryfikacja: API2/2 (deduplikacja dwóch równych kwot, retry, zachowanie checkpointu przy awarii, aktualizacja potwierdzenia, izolacja, brak sesji, odrzucenie spóźnionego zapisu po pauzie); adapter3/3 (NIM kanoniczny blok i finalność, zła sieć, Polygon i25 zdarzeń jednego bloku na dwóch stronach, obcy token); UI1/1 plus pełne testy istniejącego centrum wyjątków6/6. TypeScript API/web przechodzi. Końcowy ponowny przebieg po rozszerzeniu sprawdzania tokenu jest zapisywany w raporcie integracji. PL-08, natywna baza oraz odbiór rzeczywistych RPC i telefonu pozostają otwarte.

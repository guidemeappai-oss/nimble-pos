# MM-03: Tryb dużego ruchu

**User Story:** Jako kierownik chcę regulować przyjmowanie zamówień, aby dopasować kolejkę do wydajności lokalu.

**What to build:** Kompletny przepływ na telefonie, przez publiczne API do trwałego zapisu i ponownego odczytu.

**Blocked by:** MM-01, MM-02

**Status:** implemented-local — API, interfejs i regresja gotowe. Code review zamknięty: aktywna pauza jest zachowywana po ponownym zamknięciu bez czasu, a obliczenie zajętości kolejki jest współdzielone przez publiczny status lokalu i tworzenie wycen. Wyniki: `docs/product/merchant-management-running.md`.

## Kryteria odbioru

- [x] Pauza na określony czas, domyślny czas przygotowania i limit kolejki obowiązują przy tworzeniu zamówień i nowych wycen.
- [x] Ponowne otwarcie wymaga świeżej obecności i aktywnej zmiany; termin pauzy jest trwale zapisany.
- [x] Aktywne wyceny zachowują kwotę i mogą być opłacone podczas pauzy lub pełnej kolejki; zaakceptowane terminy przygotowania nie zmieniają się po edycji ustawień lokalu.

Limit kolejki obejmuje zgłoszone/weryfikowane płatności, opłacone zamówienia oczekujące na decyzję lub realizację oraz aktywne wyceny do ich wygaśnięcia. Nieopłacony koszyk bez aktywnej wyceny nie blokuje miejsca.

## Testy i zakończenie

Testować publiczne zachowanie API z bazą i interakcje telefonu: główny scenariusz, brak uprawnień, izolację lokalu, retry i utratę połączenia tam, gdzie wpływają na wynik. TypeScript, właściwa regresja i code-review przed zakończeniem. Etap daje samodzielnie demonstracyjny rezultat; nowe schematy i interfejsy powstają razem z obsługiwanym przepływem.
